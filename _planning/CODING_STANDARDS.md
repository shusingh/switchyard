# Switchyard: Coding Standards

The bar is **production quality**: code a senior reviewer at an infrastructure
team would approve without asking for rework. When this document is silent,
follow the references below in this order of precedence:

1. [Effective Go](https://go.dev/doc/effective_go) and
   [Go Code Review Comments](https://go.dev/wiki/CodeReviewComments)
2. [Google Go Style Guide](https://google.github.io/styleguide/go/)
   (Guide, then [Decisions](https://google.github.io/styleguide/go/decisions),
   then [Best Practices](https://google.github.io/styleguide/go/best-practices))
3. [Uber Go Style Guide](https://github.com/uber-go/guide/blob/master/style.md)
   (especially: errors, goroutine lifetimes, mutexes, channel sizes, time)
4. [Go Proverbs](https://go-proverbs.github.io/)

Where these sources disagree, prefer the Google guide and record the choice
here.

---

## 1. Core principles

- **Clarity over cleverness.** Code is read far more than written. Optimize for
  the reader who arrives cold.
- **Simplicity.** The simplest design that meets the requirement. No speculative
  abstraction, no interfaces with one implementation "for later", no
  configuration nobody asked for.
- **Correctness first, then measured performance.** Optimize only the hot path
  (keying, index, policy pick, proxy relay), and only with a benchmark that
  shows the win.
- **Consistency.** Match the surrounding code. A new pattern needs a reason.
- **Small, reviewable changes.** One logical change per commit.

## 2. Content rules (non-negotiable)

- **No references to code-generation tools or tool authorship anywhere**: not in code,
  comments, docs, commit messages, branch names, test data, or file names. No
  "generated by", "assisted by", co-author trailers, or tool names.
- Domain vocabulary is fine and expected: *LLM*, *model*, *inference*,
  *OpenAI-compatible API*, *vLLM*. Avoid vague marketing terms in prose;
  say what the thing is ("LLM inference router").
- No secrets, tokens, internal hostnames, or personal data in the repo. Config
  examples use placeholders.
- **Never log prompt or completion content.** Log sizes, hashes, and IDs.

## 3. Tooling and formatting

- Go **1.27**. The `go` directive in `go.mod` matches.
- `gofmt` and `goimports` formatting is mandatory (enforced by the linter).
- Import grouping: standard library, blank line, third-party, blank line, this
  module.
- `golangci-lint` v2 with the config below must pass with zero findings. A
  `//nolint` directive must name the linter and give a reason:
  `//nolint:gosec // G404: math/rand is fine for tie-breaking, not security`.

`.golangci.yml`:

```yaml
version: "2"
linters:
  default: standard        # errcheck, govet, ineffassign, staticcheck, unused
  enable:
    - bodyclose            # HTTP response bodies are closed
    - contextcheck         # contexts are propagated, not replaced
    - errorlint            # errors.Is / errors.As / %w used correctly
    - gocritic
    - gosec
    - misspell
    - nilerr
    - noctx                # HTTP requests carry a context
    - revive
    - sloglint             # consistent slog usage
    - unconvert
    - unparam
    - usestdlibvars
  settings:
    revive:
      rules:
        - name: exported
        - name: package-comments
        - name: var-naming
        - name: indent-error-flow
        - name: error-strings
        - name: receiver-naming
    sloglint:
      kv-only: false
      attr-only: true      # slog.String("k", v), not loose key-value pairs
      no-global: "all"     # loggers are injected, never slog.Default()
formatters:
  enable:
    - gofmt
    - goimports
```

## 4. Package and file design

- Code lives under `internal/` unless it is intentionally a public API. `cmd/`
  packages contain wiring only: flags, config, construction, signals.
- A package has one clear purpose, stated in its package doc comment
  (`doc.go` when the comment is long).
- **Package names:** short, lowercase, singular, no underscores, and never
  `util`, `common`, `helpers`, `misc`, or `types`.
- Avoid stutter: `prefix.Index`, not `prefix.PrefixIndex`.
- **Interfaces belong to the consumer**, are small (one to three methods), and
  exist only when there are two implementations or a test seam that genuinely
  needs one. Return concrete types; accept interfaces.
- No package-level mutable state. No `init()` except for registering static
  things that cannot fail. Dependencies are passed explicitly (constructors take
  what they need).
- Files stay focused; split around 500 lines. Order within a file: types and
  constructors first, then methods, then helpers.
- No circular dependencies; respect the dependency direction in DESIGN
  section 5.

## 5. Naming

- MixedCaps only. Initialisms keep a consistent case: `ID`, `URL`, `HTTP`,
  `TTFT`, `KV` (`backendID`, `ttftSeconds`, `NewHTTPServer`).
- Name length scales with scope: `i`, `b` in a three-line loop; descriptive
  names for fields and package-level identifiers.
- Receivers: one or two letters, consistent across a type's methods, never
  `this` or `self`.
- Getters have no `Get` prefix (`b.Healthy()`, not `b.GetHealthy()`).
- Units in names when a type does not carry them: `timeoutMS` is wrong, use
  `time.Duration`; for counts use `promptTokens`, `blockBytes`.
- Booleans read as predicates: `healthy`, `isStreaming`, `hasUsage`.

## 6. Comments and documentation

The goal is comments that earn their place. Too few and the reader guesses;
too many and the signal drowns.

**Required**

- A doc comment on **every exported** identifier and every package, starting
  with the identifier's name and written as a full sentence:
  `// Index tracks which backends are believed to hold each prompt prefix.`
- A comment wherever the **why** is not obvious from the code: invariants,
  concurrency rules, non-obvious trade-offs, references to external behavior
  (for example, "vLLM only caches full blocks, so a trailing partial block is
  never hashed.").
- Lock ownership on every struct with a mutex: which fields the mutex guards.
- Units and ranges on fields and parameters when not carried by the type.
- A link to the DESIGN section for non-trivial algorithms
  (`// See DESIGN.md section 9.`).

**Forbidden**

- Comments that restate the code (`// increment counter` above `n++`).
- Commented-out code. Delete it; git remembers.
- Change history in comments ("added in phase 3", "fixed bug"). That belongs in
  commit messages.
- Decorative banners and section dividers.
- `TODO` without an owner and a tracked reason. Format:
  `// TODO(shusingh): switch to binary search if BenchmarkMatch16 regresses (issue #12).`

## 7. Errors

- Errors are values. Handle each one exactly once: return it (with context) or
  log it, never both.
- Wrap with context using `%w`: `fmt.Errorf("scrape metrics from %s: %w", b.URL, err)`.
  Context reads as a chain of lowercase phrases without "failed to" or "error".
- Sentinel errors (`var ErrNoHealthyBackend = errors.New(...)`) for conditions
  callers branch on; custom types when callers need fields. Check with
  `errors.Is` and `errors.As`, never string matching.
- Error strings are lowercase with no trailing punctuation.
- **No panics** in library code for recoverable conditions. A panic is allowed
  only for programmer errors that cannot occur in a correct program (for
  example, an impossible enum value), and the HTTP server recovers panics per
  request, logs them, and returns 500.
- Validate at boundaries (config load, request decode) and trust internal
  invariants afterward.

## 8. Concurrency

- **Every goroutine has an owner and a guaranteed exit.** Long-lived goroutines
  take a `context.Context` and stop on cancellation; the owner waits for them
  (`sync.WaitGroup` or `errgroup`) during shutdown. Integration tests run
  `goleak.VerifyNone`.
- `context.Context` is the first parameter of functions that do I/O or may
  block. Never store a context in a struct (except request-scoped types that are
  themselves short-lived and documented as such). Never pass `nil`.
- Prefer a mutex for protecting shared state and channels for transferring
  ownership or signaling. Keep critical sections short; never do I/O while
  holding a lock.
- Document lock ordering if a code path takes more than one lock. Better: design
  so it never does.
- Use `sync/atomic` typed values (`atomic.Int64`) for simple counters on the hot
  path.
- Channels are unbuffered or size one unless a larger buffer is justified in a
  comment with the reasoning.
- Mutexes are fields named `mu`, placed above the fields they guard, and are
  never embedded or copied.
- All tests run with `-race`.

## 9. HTTP and I/O

- Never use `http.DefaultClient`, `http.Get`, or a server without timeouts.
  Every server sets `ReadHeaderTimeout`; every transport sets dial, TLS, and
  response-header timeouts.
- Every request is built with `http.NewRequestWithContext`.
- Every response body is closed (`defer resp.Body.Close()`) and drained when the
  connection should be reused.
- Limit request body size (`http.MaxBytesReader`).
- Stream, do not buffer, response bodies on the proxy path. Flush SSE events with
  `http.ResponseController`.
- Handle `Write` errors on the client connection: a failed write means the
  client is gone, so cancel upstream work.

## 10. Logging and metrics

- `log/slog` with a JSON handler, injected as a `*slog.Logger` (never the
  global default). Use typed attributes (`slog.String`, `slog.Int`,
  `slog.Duration`).
- Levels: `Debug` for developer detail, `Info` for lifecycle and access logs,
  `Warn` for degraded but handled situations, `Error` for failures that need
  attention. No logging in hot loops at `Info` or above.
- Every request-scoped log carries `request_id`.
- Metric names follow Prometheus conventions: `switchyard_` prefix, base units
  (`_seconds`, `_bytes`), `_total` for counters. Label cardinality is bounded
  (backend ID and policy yes; tenant only if the tenant set is configured and
  small; never request IDs or prompts).

## 11. Configuration

- One typed config struct, loaded from YAML with unknown fields rejected, then
  defaults applied, then validated once at startup with errors that name the
  field and the fix.
- Durations are `time.Duration` in Go and strings like `"250ms"` in YAML.
- No config read from the environment deep in the code; `cmd/` reads flags and
  environment and passes values down.

## 12. Testing

- Standard library `testing` for tests. `github.com/google/go-cmp` for
  structural diffs; `go.uber.org/goleak` for leak checks. No assertion
  frameworks.
- **Table-driven tests** with named cases and `t.Run`. Use `t.Parallel()` where
  the test is independent.
- Failure messages state input, got, and want:
  `t.Errorf("Match(%v) = %d, want %d", hashes, got, want)`. Prefer
  `got`/`want` naming and `cmp.Diff(want, got)` with a `(-want +got)` note.
- Test behavior through public APIs; test unexported helpers only when they hold
  real logic.
- **Deterministic tests:** no sleeps for synchronization (use channels or
  `testing/synctest`), injected clocks for time-dependent logic, fixed seeds for
  randomness.
- Fuzz tests for every parser and the canonicalizer. Keep the seed corpus in
  `testdata/fuzz/`.
- Benchmarks for hot-path functions use `b.Loop()` and `b.ReportAllocs()`;
  record significant results in the PR or commit message
  (`benchstat` output for comparisons).
- Integration tests use `httptest` servers and the simulator; they must run
  without a GPU and without network access.
- Coverage is a signal, not a target. Critical packages (`prefix`, `scheduler`,
  `admission`, `proxy`) should be thoroughly covered, including error paths.

## 13. Dependencies

- Standard library first. Each external dependency needs an entry in the DESIGN
  decision log stating why the stdlib is insufficient.
- Pre-approved: `github.com/prometheus/client_golang` (metrics),
  `go.yaml.in/yaml/v3` (config), `github.com/google/go-cmp` and
  `go.uber.org/goleak` (tests only). Phase 8 only: `github.com/go-zeromq/zmq4`,
  a msgpack library.
- No web frameworks, no logging libraries, no dependency injection frameworks.
- Keep `go.mod` tidy (`go mod tidy` clean) and run `govulncheck ./...` before
  releases.

## 14. Performance discipline

- The hot path is: decode minimal fields, key, match, pick, proxy relay.
  Allocations there are measured and justified.
- Reuse buffers with `sync.Pool` only when a benchmark shows it helps.
- Do not parse full response JSON on the stream path; inspect only what DESIGN
  section 11 requires.
- Measure before and after any optimization and record the numbers in the
  commit message.

## 15. Security

- Treat all request input as untrusted: size limits, strict decoding of the
  fields we read, no reflection of raw input into logs or headers.
- Tenant keys are compared in constant time (`crypto/subtle`).
- Explain headers are off by default because they reveal internal topology.
- `math/rand/v2` is fine for load-balancing randomness; `crypto/rand` for
  anything security relevant.

## 16. Git and commits

- **Author:** the repo owner (`shusingh <ksingh.shubh@gmail.com>`). **No
  `Co-Authored-By` trailers, no "Generated with" lines, no tool attributions.**
  A local `commit-msg` hook rejects messages that contain them.
- Message format ([Conventional Commits](https://www.conventionalcommits.org/)
  style):

  ```text
  <type>(<scope>): <imperative summary, max 72 chars>

  <body: what and why, wrapped at 72 columns; benchmark numbers if relevant>
  ```

  Types: `feat`, `fix`, `perf`, `refactor`, `test`, `docs`, `build`, `ci`,
  `chore`. Scope is the package or area: `feat(prefix): add chained block hashing`.
- One logical change per commit; the tree builds and tests pass at every commit.
- Branches: `main` is always releasable. Work on short-lived branches named
  `<type>/<short-topic>` (for example, `feat/prefix-index`) and merge with a
  fast-forward or squash.
- Never force-push `main`.

## 17. Review checklist (self-review before every commit)

- [ ] Does it do one thing, and is that thing in PLAN.md?
- [ ] Are errors wrapped with context and handled once?
- [ ] Does every goroutine have an exit path tied to a context?
- [ ] Are all HTTP bodies closed and all requests context-bound?
- [ ] Are exported identifiers documented, and are comments about why, not what?
- [ ] Are there tests for the new behavior, including an error path?
- [ ] Did `go vet`, `golangci-lint run`, and `go test -race ./...` pass?
- [ ] Is anything logged that could contain prompt content? (It must not be.)
- [ ] Are DESIGN, PLAN, and HANDOFF updated if needed?
- [ ] Does the commit message follow section 16?
